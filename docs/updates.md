# Public update discovery and gated Windows delivery

Rootlith reads only published release metadata from `KlowzyZ/Rootlith-Studio` over HTTPS, without credentials. Private Drafts and other repositories are never update feeds. There are currently no published binary releases: an empty list reports **unavailable**, never “up to date”. Metadata discovery does not authenticate an executable or authorize installation.

## Current behavior

Electron main checks about 20 seconds after the renderer loads, then about every 24 hours when **Automatically check for updates** is enabled (the default). Offline/failed requests use exponential backoff starting at one minute, bounded to a day. GitHub 403/429 responses wait at least 15 minutes and honor Retry-After/rate-reset headers; repeated manual clicks do not bypass that limit. Other manual requests have a one-minute cooldown. There is only one in-flight request shared by automatic/manual checks. Quit aborts the request and stops scheduling.

Requests have an 8-second timeout and a 128 KiB decoded response/20-entry limit, reject redirects and malformed or mismatched tag/version/channel metadata, and compare strict Semantic Versions including alpha/beta/rc ordering and build metadata. Stable versions default to stable only; prerelease builds default to previews. The user can explicitly change that preference. A full bounded window that cannot establish a newer release reports unavailable instead of asserting current-version status. Release notes are bounded to 12,000 characters and rendered as escaped text, never HTML or executable Markdown.

Settings shows installed/source version, channel, check progress, last successful query, available metadata, notes, retry time, build mode and official release links. It receives fixed events from main; browser development mode has no native updater and cannot start background or manual network checks. Source builds are labelled as source, not official installed releases. OS notifications are best effort and deduplicated by version across restarts. Settings remains authoritative when the OS suppresses a notification.

Preferences, last successful check/publication, retry schedule and last notified version live in a small schema-checked `update-preferences.json` directly under the existing `%APPDATA%\fixflow-studio` profile. Cached metadata is labelled as saved, never a fresh check. This separate file never replaces/migrates/resets investigation, backup or raw recovery records. Atomic preference writes use the existing durable-write helper. A damaged preference file is retained; automatic networking stays off until explicitly saved. A preference-save failure is not acknowledged as success.

Enabling background discovery means contacting api.github.com. It sends normal HTTP metadata (including the device's network address) but no workspace, target, evidence, token or account information. Disable it in Settings to prevent scheduled requests; manual checking remains an explicit action.

## Executable delivery: blocked

There is no Download/Install button, binary fetch, process-spawn bridge, unattended installation option or self-replacement code in this change. No automatic-download toggle is offered because downloads are not supported yet. Release pages are opened only on user request through an enum-only, trusted-sender IPC handler. No network response can supply an arbitrary external URL to that handler.

The project has **no verified publisher signing identity or pinned independent update-manifest key**, and no native Windows NSIS upgrade/portable-replacement acceptance for this new channel. Hashes fetched from the same release as an EXE are not publisher authentication. We do not add electron-updater until a real trusted publication/installation policy can be exercised. This is an intentional delivery gate, not simulated update success.

Registry/source review identified electron-updater 6.8.11 and its NSIS publisher-name/signature verification path as the prospective integration. The inspected upstream NsisUpdater rejects absent publisher names unless signature verification is explicitly disabled; this project must never use that opt-out. The appropriate prospective NSIS integration is that maintained path, using a pinned, verified publisher identity and its signature/integrity verification. Adding it requires a security review of the then-current package and actual generated metadata. Do not disable signature validation, accept arbitrary publisher names, or expose quitAndInstall to the renderer. A separately signed manifest with a pinned public verification key is another possible publisher-authentication layer; private keys belong only in a protected signing service/environment, never source or app bundles. No identity or key is invented here.

## Future publication workflow and activation gates

Use GitHub Releases in this repository; do not create a new release repository. Public PR source checks remain read-only and have no packaging/signing credentials. Follow this order for a separately approved binary release:

1. Review and merge a public PR via Main-Protection and successful `checks`. Pin the approved full commit and lockfile. Do not execute fork code in `pull_request_target`, credentialed jobs or self-hosted runners. Import source into private delivery only through a separate vetted intake with exact source hashes; no automatic public-to-private trigger.
2. On disposable Windows infrastructure without release credentials, build the pinned source and verify legacy appId `org.klowzy.fixflowstudio`, package/product filename, NSIS GUID `c41b684f-fd57-5c09-b4a7-68101139f192`, per-user/no-elevation policy and `%APPDATA%\fixflow-studio`. Preserve all installer identities. Run install/upgrade/uninstall, pending-write/recovery and portable coexistence tests against synthetic data. No destructive migration or reset.
3. Verify the pinned NSIS and component source archives, modified-template sources and licenses in **each** setup/portable package, all notices, original shell helper and actual wrapper/DLL inventory. Preserve Electron/Chromium notices and complete corresponding-source delivery obligations in PACKAGING_NOTICES.md. Do not use historical private Draft artifacts.
4. Establish and independently verify the publisher signing identity/key. Sign only independently reviewed build hashes in a protected environment, separated from untrusted build scripts. A future minimal upload job can receive `contents: write` after environment approval; the build/PR jobs must keep read-only tokens and no signing secrets. The manual `release-readiness.yml` workflow is a credential-free source/identity gate; it does not build Windows binaries or publish anything.
5. Before activating any downloader, bind publisher authentication to exact repository, version, channel, architecture, mode, asset name, hash and size. Reject downgrades, unexpected hosts/redirects and oversized or truncated streams. Use a fixed main-owned staging directory, safe filenames/exclusive writes, streaming limits and cancellation/cleanup; never use a remote path. Reject invalid signatures/hashes **before** install. Test these adversarial cases against a real implementation before exposing delivery UI.
6. Installed NSIS: after native validation, offer an explicit install-at-a-safe-time action. Reuse the renderer close handshake to commit pending edits, then drain NativeStorage. Cancel active diagnostics. On save failure, stay open. Only a main-owned verified artifact may reach the installer; no arbitrary executable or command-line input from renderer/manifest. Respect per-user/no-elevation policy. Unattended install stays disabled.
7. Portable: do not overwrite the running EXE. Offer a verified download only after publisher authentication is available, then require closing all instances and user-controlled replacement of the original launcher. Preserve the profile and recovery data. A safe atomic external replacement helper requires its own native/signature review; it is not assumed to exist.
8. Publish only newly approved signed artifacts and matched updater metadata/notes. Check public anonymous URLs and end-to-end upgrade from the actual prior installer. Document signing/provenance and exact source/binary hashes. Enabling actual delivery requires a reviewed code/configuration change and native evidence; publishing metadata alone cannot activate execution in the current client.

## Verification limits

Controlled fixtures cover discovery, semver/channels, malformed/oversized/redirected responses, offline/API failures/rate limits, progress/concurrency, daily scheduling, persistence/restart deduplication, preference failures, request cancellation and unchanged recovery/workspace bytes. Download-host, publisher-signature, binary-hash, download cancellation and installer recovery tests remain **blocked with the download/install implementation**; no passing downloader tests or native Windows acceptance are claimed. Linux source checks do not establish Windows behavior.

Reference review: SightSweep and LanternDrop currently expose docs/assets rather than reusable update implementation. OZFA-Disk-Control separates update checking, scheduling, settings and notification from execution; this change uses the same separation concept with original TypeScript code, not copied WPF/.NET code. Other projects and the private internal repository were not modified.
